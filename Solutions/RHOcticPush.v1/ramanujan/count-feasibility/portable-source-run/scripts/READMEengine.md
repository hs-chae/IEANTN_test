# Physical-aware clean-source replay engine

This is an additive resource-only variant of the existing pinned `portable/scripts/reproduce_profiled_closure.py`. The original engine, numerical sources, source parser, C programs, mathematical statements, compiler invocation and per-module address-space profiles remain unchanged. The composition wrapper and its source/receipt validation are maintained separately by the count workstream.

The old scheduler added virtual address-space ceilings. That restricts a300GiB sum to two128GiB proof jobs even when actual child memory is about32GiB and much more RAM is available. This engine instead admits at most22 workers from actual available RAM, observed owned compiler-tree RSS and possible remaining worker growth, while preserving at least512GiB for the host. Each ordinary worker receives a physical forecast of at least39.6GiB or120% of the largest completed child peak, capped by that worker's existing address-space ceiling. A256GiB-or-larger profile runs alone and reserves its whole ceiling physically. Thus128/256GiB address-space limits remain limits on each compiler, not claims that each process actually consumes that RAM.

Before every dispatch, available RAM must cover the host reserve, the sum of all active workers' forecast-minus-observed-RSS positive parts, and the next worker's forecast. Every admission and release is recorded and rechecked. The sum of virtual address limits is retained as an informational field and can exceed300GiB. It is never reported as measured RAM. The launch still requires genuinely available1TiB for a per-task ceiling above48GiB, as did the original high-resource engine. A small smoke run may use48GiB profiles and a48GiB ceiling when the independent host-reserve check passes.

`--address-ceiling-gib` names the per-task maximum clearly. `--aggregate-gib` is retained only as a documented compatibility alias for that same per-task parameter in this new engine. It no longer limits the sum of virtual address spaces; the old engine retains its old meaning unchanged. The resource policy and journal schema explicitly distinguish the two engines.

The wrapper places the unchanged `rebuild_qrh_closure.py` parser beside this engine inside `engine/Solutions/Replay/scripts/`. Invoke the engine there with the pinned generic context, exact application source directory, actual target module and theorem names, exact resource profile, and a fresh output directory. For example, the full-count wrapper supplies128GiB arithmetic profiles,256GiB final/audit profiles,22jobs, separate CPU lanes, `--address-ceiling-gib300`, and `--host-reserve-gib512`. The generic engine alone is not a source/data regeneration wrapper or a source-first program-verification proof.

Successful runs publish `RESULT.json` atomically only after complete source/object/log/axiom and resource-journal validation; `CANDIDATE.json` is not acceptance. `--check RUN_DIRECTORY` rechecks the result. `RESOURCE_SAMPLES.jsonl` records compiler-tree RSS and owned regular-file bytes approximately once per second, including the final audit. These are sampled aggregate measurements. GNUtime supplies the individual child RSS high-water marks. Shared mapped pages may be counted more than once in RSS; no exact physical-usage or PSS claim is made.

SIGINT, SIGTERM or SIGUSR1 stops further dispatch and lets currently owned compiler children finish. The engine then saves `STOPPED.json` with `REQUESTED_DRAIN_NOT_ACCEPTANCE`; partial objects, source snapshots and failed attempts remain evidence. A host-reserve shortfall terminates only exact PID/starttick-matched owned process groups and records `RESOURCE_STOP.json`, distinguished from OOM evidence. The engine never signals historical jobs or unrelated workspaces.

`ENGINE_RESOURCE_DIFF.patch` and `ENGINE_RESOURCE_DIFF_AUDIT.json` expose the exact difference from the pinned original. Protected source-discovery, numerical compiler-command and axiom-checking fragments are independently byte-compared. Resource-gate tests run actual normal, `-O` and `-OO` CLIs on explicitly synthetic scheduling journals, including a valid three-job case whose virtual-address sum is384GiB while its physical forecast is much smaller. Those fixtures are not Lean proofs, numerical certificates, or observed operating-system resource measurements. A separate actual clean small-N application smoke is required before claiming the composition is executable.

The compiled program and mathematical claims retain their established compiler, runtime, OS/API, hardware and model-interpretation trust boundaries. This Python scheduling change is not source-first PV and adds no mathematical hypothesis.
