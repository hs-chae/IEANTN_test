# MomentPNT.v1 public source solution

`Solution.lean` proves the six current challenge types. The first five proofs are
copied from the accepted adapter without mathematical edits; the additional
prime-rich conclusion uses only the existing future moment profile.

Three conclusions use the two actual C programs' physical output reads through
`SynergyMomentCHi.FinalProgram`. They keep the unchanged14 mathematical input
interfaces. The two direct-vector comparisons remain ordinary-kernel verification,
not source-first program verification. The derived prime-count conclusion uses
only `moment_future_pi`. The sources contain no import of an admitted Challenge.
The challenge template is compiled separately solely to compare the exact six
expected types in a different Lean environment; it is never a Solution premise.

## Included source and dependencies

The complete source-only moment4486 and vector568 capsules are under Dependencies.
Their565 overlapping application modules have identical source bytes. Their prior
compiled objects need not be byte-identical, so this solution never mixes those
banks: it uses one validated4486 read-only parent and freshly compiles the vector
three-module extension. The exact core source snapshot is under Core. A source
registry pins every physical source root and byte hash. The normal Lake project
also registers all support libraries at these real source roots and takes the
actual IEANTN core as its path dependency; it is not a placeholder missing library.
The reproducibility script below is the measured proof route; a Lake build alone
does not attest numerical regeneration or an isolated source-first chain.

Use Lean4.34.0-rc2, commit6a10ac8c22beadecabdbb0919c2b50214762f91d, and
Mathlib71a80585ee495fc24472fd0eaffc89d94e4fd8d6. PINNED_ENVIRONMENT.json records
the exact compiler/runtime hashes and eight public generic dependency commits.
No private application object path is an environment parameter. Locate an existing
public generic installation, or obtain/build those exact commits, then run:

```sh
python3 -B prepare_environment.py --toolchain /absolute/lean-4.34.0-rc2-linux \
  --mathlib /absolute/public-mathlib --packages /absolute/public-mathlib/.lake/packages \
  --out /absolute/fresh-environment.json
```

The packages argument may point to another directory containing the exact eight
public dependency checkouts. Their generic compiled libraries must be available
at each checkout's .lake/build/lib/lean. The script checks compiler/runtime hashes,
Git commits and source/object placement. It does not download or update a package.
Do not use a foreign Lean toolchain's objects.

## Check the package and reproduce

Run from this solution directory. Every output directory must be fresh and outside
this source package:

```sh
python3 -B reproduce.py --check-inputs-only --out /absolute/fresh-input-check
python3 -O -B reproduce.py --check-inputs-only --out /absolute/fresh-input-check-O
python3 -OO -B reproduce.py --check-inputs-only --out /absolute/fresh-input-check-OO
```

This validates sources and import coverage, not mathematical completion. To rebuild
from clean application source without a prior application object bank:

```sh
python3 -B reproduce.py --environment /absolute/fresh-environment.json \
  --out /absolute/fresh-complete-run
```

That route actually runs the full existing4486-source recipe, including its4057
source parent and numerical/C/build/link/CRT/observation regeneration. It can take
hours and requires a suitable resource lease, typically up to256GiB for the large
parent. It then builds the exact new core interfaces, vector modules, derived
helper and actual Solution, audits all six typed closures, and checks their exact
Challenge types in separate environments. The fresh route is a source reproduction;
isolation must be established by an outer namespace runner, not inferred from this
script's success. The accepted historical parent already has its separate paired
namespace and mathematical receipts.

For the shorter explicitly chained route, supply the exact independently accepted
4486 same-pipeline parent whose complete source/build/numerical/object manifest is
pinned in Evidence/PARENT4486_LOCK.json:

```sh
python3 -B Isolation/launch.py --environment /absolute/fresh-environment.json \
  --moment-parent /absolute/accepted4486/namespace/data/run \
  --out /absolute/fresh-isolated-append
```

This mounts that exact parent read-only and denies unrelated workspace/history or
application caches. Only the pinned public generic tools/libraries, source package,
accepted parent, explicit environment file and owned output are visible. It checks
distinct process/mount/offline-network namespaces and current source/object hashes.
The application bank is explicitly not empty. It freshly recompiles the three
vector modules, three new core interfaces, helper and Solution. Actual proof,
exact-type, namespace and resource receipts are separate; this is not an official
IEANTN Comparator workflow receipt. Any parent other than the exact pinned accepted
one is refused rather than described as source-cold by its own status string.

Use the existing aggregate resource harness around either proof command. The
adapter imports have measured process RSS above8GiB;16GiB is a sensible bounded
append reservation, while the complete clean parent needs substantially more.
Available RAM and scratch are separate capacities. No obsolete4GiB cap applies.
