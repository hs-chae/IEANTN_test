Should verified programs be IEANTN nodes?

Decision brief · Agent B · 2026-11-06 · upstream teorth/IEANTN@466b41b, PoC hs-chae/IEANTN_test@qrh-2pv_B 3280a3c

No, not as a rule. A verified program is evidence for a mathematical conclusion, and IEANTN already keeps evidence apart from claims. Keep programs, sources, certificates and native facts with the conclusion they prove (evidence only). Give a numerical result its own node only when a rule says so (below), and state it as mathematics, never as a program.

A theorem and a verification artifact are different objects

Mathematical conclusion (a node)

  • A Lean Prop in Conclusions.lean, e.g. HasNumericalBound Eπ (5/10^16) (exp 330)
  • Imports other nodes' statements, never their proofs
  • Fingerprinted; changing it means a new version
  • Anyone can use it without knowing how it was checked

Verification artifact (evidence)

  • C source, decoded literals, certificate, soundness proof, native facts, source hash
  • Lives in a solution project and in the justification metadata
  • Can change (new program, fewer native facts) while the statement stays fixed
  • Its trust tier is a property of the evidence, not of the claim

The experiment

In a disposable worktree a C-program-verified bound was registered as its own node: 5 files and 128 lines, a 15.6 s core rebuild, and no existing fingerprint moved. Its one-line solution matches the challenge exactly with only the three standard axioms, so it is Comparator-eligible in shape (no Comparator was run, no receipt exists). Changing bytes in the C file never moved the statement's fingerprint and always rebuilt the certificate, but the repository's drift check could not see the change from the node's own project. Separately, upstream's bridge rule, which the PoC branch predates, rejects four PoC re-designations that made unconditional results rest on QRH: changing the designated proof route also needs that guard.
